# T1.1 Characterization: schema evolution parity

## Scope

This leaf adds executable C# characterization only. It does not introduce a
V2 API or change production behavior. Bun remains the behavioral reference
through its existing schema migration, rollback, snapshot-diff, and
existential-versioning suites.

## Bun reference evidence

The following focused command passed with `16 pass`, `0 fail`, and `75`
assertions:

```text
/Users/kongweixian/.bun/bin/bun test \
  ./__tests__/om-schema-migration-apply.test.js \
  ./__tests__/om-schema-rollback.test.js \
  ./__tests__/om-schema-snapshot-diff.test.js \
  ./__tests__/om-existential-versioning.test.js
```

Those suites establish the already-supported Bun baseline: omitted `strict`
means strict migration preflight; a rejected incompatible value-type change
keeps schema state at v1; a failed later step removes earlier writes; strict
rollback blocks incompatible current data; force rollback returns diagnostics;
rollback restores aliases and historical rules; and schema diff is keyed at
definition level (including existential rules).

## C# characterization evidence

Added `cozo-lib-dotnet/tests/SchemaEvolutionParityFixtures.cs` and the focused
test-harness selector `COZO_OM_TEST_FOCUS=schema-evolution`. The fixture passes
while deliberately asserting the current legacy behavior that V2 must replace:

1. `new SchemaMigrationSpec(...)` defaults `Strict` to `false`, and even a
   call with `Strict: true` changes a string property definition to `Number`
   despite a stored non-numeric value. This characterizes missing strict
   preflight.
2. A migration with `addType` followed by an unsupported step throws but leaves
   the first type present while schema state remains v1. This is direct
   observable evidence of non-atomic application.
3. A `strict: true` rollback to a required numeric attribute completes when
   v2 data contains a non-numeric string, confirming the legacy `strict`
   argument is not an enforcement boundary.
4. Legacy data rows survive `InitSchemaAsync`, but the facade returns `Task`
   only and exposes neither legacy detection diagnostics nor an explicit
   upgrade result. Detect-only initialization and explicit idempotent upgrade
   therefore remain V2 work rather than a claimed current capability.
5. `SchemaDiff` returns complete source/target snapshots in `Added` and
   `Removed` plus only `{ from, to }` in `Changed`; it does retain C# behavior
   metadata in those broad snapshots, but it is not Bun-style keyed diff yet.

The C# validation command passed with build warnings/errors both zero:

```text
/usr/local/share/dotnet/dotnet build tests/Cozo.DotNet.Om.Tests.csproj --no-restore
COZO_OM_TEST_FOCUS=schema-evolution \
  /usr/local/share/dotnet/dotnet run --project tests/Cozo.DotNet.Om.Tests.csproj --no-build
```

Output: `Focused schema evolution fixture passed.`

## Track implications

This evidence supports the already-decided D2=B/D4 implementation direction:
add strict-by-default, atomic, diagnostic V2 methods; keep legacy methods as
compatibility wrappers; do not silently upgrade legacy data; and replace the
coarse diff with a keyed structure without dropping C# behavior metadata.
